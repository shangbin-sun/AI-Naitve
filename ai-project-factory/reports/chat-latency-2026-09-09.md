## 优化优先级

1. **先研究首字前的上游等待。** 两次主要耗时均在模型请求确认后，首个文字增量返回前。本地日志无法拆开提供方排队、网络、输入处理与模型推理，不能将全部等待归因于“思考”。在相同请求下对推理强度做受控对比，再决定是否调整；本次未改变生产配置。
2. **检查额外模型上下文。** 实测应用发送的业务 JSON 263 bytes、system 1,347 bytes、schema 3,192 bytes，但报告约 10.3k 输入 tokens，业务仅一条消息且没有图片/资料。提示应检查 Codex 注入的额外指令、工具定义等开销；具体来源尚未逐项证明。不能把这些 token 全部解释为用户历史对话，也不能仅因使用临时会话就断言导致缓存不命中。
3. **区分普通聊天与完整方案更新。** 目前即使问候也要求完整 `reply + draft`。可以评估普通对话不重建方案、需要变更时再生成方案的流程，必须验证没有破坏上下文与方案同步。收益尚待实测。
4. **降低本地小额开销。** 每次增量都写数据库，47 次累计约 68–70 ms；可以聚合写入，但需保留最后一段和取消时内容。SSE 100 ms 的检查周期带来本次 41–56 ms 的发送延迟，可换为事件通知。这些都不是十几秒等待的主要原因。
5. **补真实浏览器体验样本。** 当前日志测到 SSE 服务端发送，本次额外测到 HTTP 客户端收到。尚未覆盖浏览器接收、React 更新与绘制，也未统计长对话或复杂团队方案。

## 提速实施与复测（同日 15:30–15:34）

已实施并验证：

- 用会话级配置关闭发现的 17 个技能、2 个 MCP、12 个插件，以及多代理、JS REPL、应用等无关功能；全局配置保持不变。配置选项依据 [OpenAI Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference)，协议字段以本机 CLI schema 校验。不能将所有减少的 token 精确归因到某一个目录。
- 同一模型下试验 medium/low。low 两次首段延迟为 10.4、35.8 秒，未优于 medium；最终保留 `gpt-6-astra` / `medium`。测试次数少，不能得出 low 一般更慢的结论。
- 普通对话可返回 null 草稿，不再重建无变化方案；显式需求与修改依然走完整 schema 与版本校验。
- SSE 由新内容事件唤醒，替代每 100 ms 读取数据库。预览立即发布，第一段立即落库，后续 200 ms 合并写入；取消或失败会写入最后一段。成功完成以最终模型回复为准。
- 前端收到终态立即刷新，6 秒轮询作为同步兜底；增加首段接收及显示帧的内容无关测量。
- 自动记录慢首字事件（>10 秒），提供 `scripts/chat_latency.py` 汇总最近 20 条；不自动生成测试对话或消耗模型额度。

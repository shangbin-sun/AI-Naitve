# 平台驱动的员工研发：实现与边界

## 问题定位

原先的团队设计调用仅输出结构化方案，禁止执行工具。员工自动脚手架主要是职责、输入输出和示例说明。创建岗位并不等于创建可运行的软件员工。

需求分析有独立文档生成能力，但不负责执行架构、开发、测试、部署。设计评估明确不执行代码，不能作为功能质量通过的证据。已有 Gradle 基线在配置阶段要求 Nexus 发布凭据，尚未运行项目测试；失败日志没有进入开发和修复循环。部分来源只有节选，缺少已确认的输入输出配对标准。

## 本次新增的实际功能

项目 → 资料与评估 → 让系统开发员工。

1. 平台冻结来源、项目版本、目标和迭代上限。
2. 平台服务调用 Codex CLI，从参考资料整理可执行接口规则、开发样例和独立验证样例，记录来源与样例哈希。
3. 另一轮平台 Codex 调用生成 `employee.py`、`AGENTS.md`、`.agents/skills/process/SKILL.md`、单元测试和说明。开发调用只接收开发样例与通用规则。
4. 平台写入独立工作目录，执行单元测试和开发样例，直接比较程序实际 JSON 输出与冻结的期望。模型自述不作为通过依据。
5. 失败日志及开发样例差异反馈给 Codex 生成下一版完整工程；默认最多两轮，上限三轮。
6. 开发检查通过后执行独立验证。验证失败不会把隐藏答案反馈给开发器，也不登记员工。
7. 全部通过后自动登记员工工程和试运行节点，保留原团队和流程；若项目已被修改则保留工程并提示版本冲突。
8. 登记后的员工支持提交新 JSON 输入试运行，冻结员工文件和版本，持久化结果。无预期答案的运行只报告执行结果，不报告业务验收通过。

## 运行与存储

- 构建：`POST /api/workspaces/{project_id}/employee-builds`
- 查看：`GET /api/workspaces/{project_id}/evaluations`
- 停止：沿用已有 evaluation cancel API。
- 登记：自动执行；`POST /api/evaluations/{run_id}/install-employee` 支持幂等返回。
- 员工试运行：`POST /api/employees/{employee_id}/runs`，请求 `input_json`。
- 工程和测试隔离目录：`.data/employee-builds/{run_id}/`
- 员工试运行目录：`.data/employee-runs/{run_id}/`
- 来源快照、生成文件、每轮退出码、标准输出/错误、真实输出差异、哈希和员工 ID 保存在平台 evaluation 记录。

## 必须保持清晰的能力边界

当前交付的执行适配器是 Python 标准库 JSON 数据处理员工。Codex 是员工工程的构建与修复者，平台 Worker 执行生成的 Python 入口。没有声称员工试运行本身启动 Codex 读取 AGENTS/Skills；这些文件是可编辑、可导出的员工工程资产。

参考资料派生的测试标为 `derived_unapproved`，不是人类已批准的金标准。独立验证表示没有提供给开发调用，不代表独立人工制定。实际通过只能证明实现符合本次候选接口和样例，不能证明完整北汽需求覆盖。

当前本机使用 macOS sandbox-exec，限制网络、用户主目录数据读取与目录外写入，含超时、日志限制和子进程清理；这不是面向多租户生产的完整容器隔离。其他操作系统没有适配时明确失败。完整 IT 员工仍需容器/工作树执行适配器、依赖与工具绑定、Codex 工具执行会话、制品交接和阶段 DAG 调度。

对画图、开发、部署等复杂员工，应沿用同一研发生命周期，更换执行适配器与验收器：图形产物与操作结果、代码测试与补丁、部署健康检查与回滚。不能把它们都压缩成 JSON 员工，也不能用生成职责文档替代执行闭环。现有设计、工程编辑、资料导入和基线测试均保留。

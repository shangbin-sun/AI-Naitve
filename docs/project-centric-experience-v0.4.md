# AI 项目工厂：以项目为中心的体验改版

日期：2026-09-07。状态：已按用户确认实施项目筹备阶段改版；运行和资产发布仍为后续阶段。作为 v0.3 的体验与数据关系修订。

实施约束：全局只有“项目”和“员工”两个入口，项目默认打开，员工入口降低视觉权重。下文提出的模板库不设独立入口，将来复用能力放入项目或员工内部。

## 1. 当前断点

现有路径是团队设计 → 完善员工 → 创建项目快照 → 查看快照。项目中修改员工必须返回源团队，再创建另一份快照。聊天记录归属 Design，Employee 也归属 Design，Project 仅存储某个设计版本的 JSON 快照。这使项目缺少持续编辑、决策和推进的主入口；仅把入口合并或改名无法解决。

另一个交互问题是把 Drawer 铺满工作区后仍保留背景滚动。员工详情滚到底再次滑动会滚动员工列表，顶部导航随之移走。本次已增加共享背景滚动锁和详情滚动边界；嵌套详情关闭后，父页面继续持有锁，最后一个详情关闭才恢复背景滚动。

## 2. 新的主路径

新建项目 → 输入目标 → 在同一项目内补充方案 → 就绪检查 → 执行与人工处理 → 成果验收 → 继续迭代。

项目在用户提交目标时就建立稳定身份，即使 AI 生成失败也保留目标、对话和重试入口。不再要求先完成一个独立团队才能拥有项目。团队设计成为项目筹备阶段的能力，也能在后续迭代中再次使用。

例如用户提出“自动完成待办应用的需求、架构、开发、测试和本机部署”。系统立即建立该项目，生成岗位、任务依赖、输入输出和验收条件，直接进入该项目的方案页面。点击开发员工，在同一项目中修改指令；返回后保留原来的方案标签与滚动位置。补充仓库、运行环境和人工决策后，才具备发起运行的条件。

这个例子不成为通用固定流程：训练项目可采用数据准备 → 训练 → 评估 → 人工评审，内容项目采用调研 → 写作 → 审稿。

## 3. 信息架构与页面

全局导航只保留项目和员工。团队设计作为项目内的对话与方案能力；员工入口弱化，不增加模板库或最近团队等一级入口。

| 项目内页面 | 核心内容 | 用户下一步 |
| --- | --- | --- |
| 概览 | 目标、阶段、最近产出、阻塞、待我处理 | 处理最关键的阻塞或打开当前工作 |
| 项目方案 | 需求与验收、团队、工作流、待完善项 | 对话调整或直接编辑；查看变更影响 |
| 工作 | 运行批次、任务状态、交接、日志、失败原因 | 查看任务、暂停、重试或处理人工任务 |
| 资料与成果 | 输入资料、工作文件、输出版本及其引用关系 | 上传、浏览、编辑、评审或打开浏览器 IDE |
| 资源与设置 | 仓库、运行环境、工具、权限、预算 | 检查依赖并定位缺失配置 |

未实现运行与文件服务前，仅交付可用页面，说明当前能力边界。项目概览不能把“设计完成”展示为“项目完成”。

所有复杂详情使用完整工作区页面及明确面包屑，例如“项目 / 方案 / 开发员工”。通过 URL 表达项目、标签和详情身份，支持刷新、浏览器前进后退和分享位置。保留列表筛选、标签、滚动位置；未保存修改离开前提示。普通删除确认可以使用小弹窗，内容编辑不再使用叠加半屏抽屉。

## 4. 聊天怎样融入工作

项目助手属于当前项目，默认了解当前方案版本和用户所在对象。它不占用固定半屏：在方案页提供全宽对话视图与结构化方案视图切换；对象页的“让 AI 协助修改”携带员工或任务上下文进入同一项目会话，并提供返回原位置入口。

首次对话可自动生成可撤销的项目方案草稿。后续要求如“增加一个测试员工”“让测试失败回到开发”，先展示受影响的岗位、流程与验收规则，以及变更摘要；应用后保存新方案版本并给出可点击的结果。问题回答归入项目需求或决策记录，不能只留在聊天文字中。

长任务显示排队、处理中、成功、失败、取消状态；失败保留用户输入，支持重试。AI 生成期间人工修改导致版本冲突时，保留提案，要求重新合并，不能覆盖新修改。对话刷新后可恢复。

## 5. 员工开发仍然有独立价值

项目员工负责“这个项目如何工作”：职责、项目指令、输入输出、任务、权限与资源绑定。用户在项目内就能修改，无需绕到员工开发页。

员工开发负责“能力如何生产和复用”：源工程、工具适配、调试样例、评测、发布版本。项目可以直接生成专用员工草稿；成熟后可另存为通用员工模板。也可以选用已发布模板，再填写本项目配置。

模板版本与项目实例分开。修改项目员工不改其他项目；升级模板展示差异与影响，逐项目选择采用。独立员工开发功能保留，但不成为普通用户创建项目的必经步骤。

## 6. 数据关系与执行边界

| 对象 | 含义 |
| --- | --- |
| Project | 持续存在的项目，包含目标、状态与当前方案引用 |
| ProjectPlanRevision | 保存需求、项目成员、流程和验收条件的方案版本 |
| ProjectMember | 项目内员工实例，可绑定模板的固定版本并保存项目配置 |
| EmployeeTemplateVersion | 员工开发发布的可复用能力版本 |
| Run | 某次执行，冻结采用的方案、员工和资源配置引用 |
| ArtifactVersion | 输入或成果版本，记录生产者、任务、来源及引用 |
| Decision / Conversation | 项目决策和对话，可关联具体任务、成员、成果 |

方案更新不改变正在运行的批次。默认从下一次运行生效；当前运行要改变计划时，通过暂停、影响检查和新版本接续记录处理。冻结资源配置引用不代表复制密钥或冻结外部服务状态。

运行前检查员工能力、流程依赖、数据输入、资源授权、人工责任人与验收规则。显示可执行的修复入口。实际执行成功、产物存在、验收通过才算完成；生成结构化方案不等于执行成功。

人修改成果时生成新版本，对使用旧版本的下游任务标记需要检查或重跑，并展示处理结果。任务交接传递成果引用与版本，员工文件夹只是查看方式，不能作为唯一的数据协议。

## 7. 分阶段交付及迁移

第一阶段先打通项目筹备：项目先创建；对话、方案、员工编辑均归项目；保存不会生成另一个项目；所有详情采用可恢复的整页导航。保留员工开发，暂不扩建运行功能。验收重点是目标 → 对话 → 修改岗位 → 返回方案 → 刷新恢复这条主路径。

第二阶段补齐依赖与执行：资源连接、就绪检查、实际任务运行、失败恢复、人工处理和产物验收。先贯通一个本机样例流程，再扩大业务类型，不以模拟状态替代真实成功。

第三阶段完善资产复用：员工工程评测与发布、项目模板、项目间选择升级，以及可追溯知识沉淀。

迁移时先备份数据库。每个旧 Design 迁入持续项目并保留会话和员工版本；同一 Design 下的旧 Project 快照保留为历史配置快照，不能伪装成已运行批次。保留旧 ID 到新页面的映射。若历史快照实际代表独立业务项目，提供复制为独立项目入口，保留原始来源；迁移不删除历史内容。上线前对迁移数量、快照内容和链接逐项核对。

## 8. 改版验收标准

1. 首次输入目标即产生可恢复项目，AI 失败后仍可打开并重试。
2. 不离开当前项目即可完成对话、岗位编辑、流程调整和问题补充。
3. 保存后同项目立即展示变更；刷新和浏览器后退能恢复正确位置。
4. 项目员工修改不会污染其他项目或模板；历史快照内容保持不变。
5. 未保存修改离开有保护；详情滚动到底不会带动背景；嵌套返回不会提前解除滚动锁。
6. AI 与人工并发编辑不会静默覆盖；变更失败保留输入并给出重试入口。
7. 未完成资源检查时清楚说明缺什么、在哪里补；未实现执行时不展示可运行假按钮。
8. 执行批次绑定固定方案；失败、重试、人工干预及成果验收有可追溯记录。

当前已实施：默认项目列表与搜索、新建时持久保存目标、同项目对话/概览/方案/历史全宽切换、项目内员工编辑、未完成方案的员工工程生成、历史快照归档、项目与员工详情 URL 恢复、未保存修改保护。存储上复用原 Design 作为持续项目，原 Project 作为方案快照，保留表和 ID 以兼容原数据及接口，无数据删除或虚构运行迁移。

尚未实施：实际执行/资源连接/成果文件服务、正式模板发布与版本升级、运行批次冻结及接续、AI 修改提案的可视化差异合并。当前 AI 生成依然直接保存方案版本并由并发版本检查保护；手动方案编辑仍为校验后的 JSON 编辑器。不能将当前筹备阶段验收视为整个产品闭环验收。

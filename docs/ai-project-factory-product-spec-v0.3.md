本文用于确认产品需求。已经达成共识的定位作为基线；首版范围、默认策略和具体交互为建议，见第 17 节待确认清单。技术设计用于说明可实施性，接口名称均为平台拟定接口。

## 1. 产品定位

AI 项目工厂（AI Project Factory，`ai-project-factory`）是一个由人类决策与干预、AI 员工执行工作的项目协作平台，内置员工工厂能力。

用户通过浏览器提出目标、组织团队、查看成果、修改资料和处理决策。AI 员工基于 Codex CLI 运行时承担具体任务。平台持有项目状态、协作记录、文件、成果版本与组织记忆，使人员和会话更换后项目仍能延续。

项目可以是调研、数据分析、模型训练、内容生产、运营或软件研发。平台不预设所有项目都经过需求、开发、测试、部署阶段。

### 1.1 已确认的设计基线

- 一个产品内置员工工厂，暂不独立建设第二个平台。
- 后端使用 Python；前端初始选择 React、TypeScript、Vite 和 Ant Design。
- Codex CLI 是初期 AI 员工执行基础，模型推理使用所配置的云端服务。
- 主要计算、文件操作和项目数据管理在服务端完成，用户无需安装本地编辑器。
- 提供浏览器 IDE；项目工作台承担日常协作入口。
- 人和 AI 都是项目成员，沟通围绕项目、任务和成果展开。
- 成果拥有身份和版本，不能仅通过员工文件夹定位。
- 人工修改需要有影响分析、处理状态和生效回执。
- 支持交接、暂停、员工替换、异常恢复及正式验收。
- 记忆更新需要依据，员工会话不是组织知识的唯一保存位置。
- 对话式团队设计作为主要创建入口：聊清团队核心信息与协作流程后自动建立可编辑草稿，再完善员工细节。

### 1.2 目标与边界

核心目标：让人以较少的协调成本，获得可验收的项目成果，同时保留理解、干预和接续工作的能力。

首版不建设通用模型训练平台、独立员工交易市场、复杂公司组织系统，也不承诺所有类型的数据都能在浏览器原生编辑。模型训练项目通过外部作业接口接入；员工能力训练也不等于在平台中直接训练 Codex 底层模型。

“数据沉淀在平台”指业务数据与可观察工作记录由平台持有和管理，不表示云端推理不传输上下文，也不要求保存模型隐藏思考过程。

### 1.3 一个产品、三个工作区域

| 区域 | 主要用户 | 职责与产出 |
|---|---|---|
| 员工开发工作台 | 能力开发者、人类或 AI 开发协作者 | 编写员工源工程，调试、评测，发布员工模板版本 |
| 项目模板中心 | 流程设计者、项目负责人 | 装配岗位、员工能力、协作流程、数据契约和验收方案 |
| 项目运行工作台 | 人类参与者与项目 AI 员工 | 绑定真实资源，执行、协作、干预并验收 |

员工工厂是独立开发子系统，拥有独立工程、调试环境与发布生命周期。它与项目运行共享身份、资产库、文件、消息和审计基础服务。员工源工程可独立 Git 仓库，Worker 可独立部署；这些不要求独立建设第二个平台。

将来出现员工资产独立客户、多上层平台消费或独立运营团队时，再评估产品拆分。

## 2. 用户、角色与职责

| 角色 | 职责 | 默认权限建议 |
|---|---|---|
| 空间管理员 | 管理成员、运行资源、平台配置 | 管理配置与成员；敏感操作另记审计 |
| 项目负责人 | 设置目标、任用员工、分配授权、最终验收 | 管理本项目与业务决策 |
| 人类参与者 | 执行分配的工作、编辑成果、提供反馈 | 按项目和任务授予 |
| 人类评审者 | 对指定成果评审或验收 | 指定成果读取、评论与评审 |
| 员工能力开发者 | 开发员工源工程、调试与评测 | 访问开发工程和测试资源；正式资源另行授权 |
| 模板设计者 | 装配岗位、流程和契约 | 编辑模板草稿与运行预演，按权限发布 |
| AI 项目主管 | 澄清目标、规划工作、处理例外、汇总进展 | 在授权内提出或更新计划 |
| AI 专业员工 | 处理具体任务、交接成果、报告问题 | 仅使用任务需要的工具和资料 |

首版建议采用单组织空间、多项目、多个人类成员；数据结构保留空间 ID，为后续扩展准备。AI 项目主管是特殊岗位的员工，其业务决定同样受平台授权约束。

## 3. 核心对象

| 对象 | 定义及关键关系 |
|---|---|
| 空间 | 项目、成员、员工模板和资源的管理范围 |
| 项目 | 目标、范围、约束、预算、成功标准与当前状态 |
| 员工工程 | 长期保存的能力源工程，包含指令、代码、工具、流程、环境声明和测试样例 |
| 员工模板版本 | 岗位职责、技能、工具需求、运行配置、交付约定及评测结果 |
| 能力入口 | 员工可被调用的具体能力，声明输入输出，例如 analyze、train、evaluate |
| 项目模板版本 | 输入表单、岗位、默认员工、阶段与协作流程、资源需求及验收约定 |
| 团队设计会话与草稿 | 保存对话、结构化团队方案、设计修订和生成对象映射，作为项目模板的团队设计入口 |
| 工作流程定义 | 节点、数据绑定、控制关系和错误策略，明确属于员工内部或项目协作 |
| 资源绑定 | 将能力所需逻辑资源映射为项目或测试环境的实际资源 |
| 评测运行 | 员工草稿／版本在固定样例与资源上的测试记录 |
| 项目员工 | 引用固定模板版本，拥有项目身份、权限和工作经历 |
| 团队关系 | 分工、委托、交接、评审和冲突升级关系 |
| 任务 | 目标、输入版本、负责人、依赖、预算和验收条件 |
| 运行 | 某次执行尝试，关联任务、员工、会话、环境及输出 |
| 外部作业 | 训练等长期计算的独立生命周期与服务方 ID |
| 成果及版本 | 稳定成果 ID、不可变版本、文件清单、作者及来源 |
| 消息 | 指定范围内的沟通，关联任务、成果或决策 |
| 决策 | 问题、选项、依据、授权人、选择及生效范围 |
| 变更请求 | 人或 AI 提出的修改及其影响、处理结果 |
| 知识条目 | 带来源、适用范围、版本和验证状态的组织知识 |
| 活动事件 | 可追踪的操作事实，记录操作者、对象、时间和结果 |

一个模板可以创建多个项目员工，一个员工可以承担多个任务，一个任务可以有多次运行。员工、任务和 Codex 会话不能合并成同一个对象。

员工工程发布后形成员工模板版本；“员工模板”就是可复用员工资产，不再另建一份重复的能力定义。流程节点代表工作，员工代表执行者。

```text
共享技能／工具声明／环境模板
              ↓ 被员工工程引用
员工工程 → 调试与评测 → 员工模板版本
                               ↓ 通过能力入口绑定岗位
项目模板版本（岗位＋协作流程＋输入输出＋验收）
                               ↓ 任用与资源绑定
具体项目 → 任务 → 运行 → 成果版本／决策／经验
```

## 4. 完整业务闭环

1. 人通过团队设计聊天描述目标，也可选择已有模板，上传资料或连接数据源。
2. AI 设计助手逐步澄清岗位、职责、工作流和交付约定，自动保存结构化草稿；信息足够后创建项目模板草稿、员工引用或新员工工程草稿，并列出待完善事项。
3. 人调整并确认必要范围和授权；已有授权内的后续常规工作直接执行。
4. 平台创建任务与依赖，任用员工，准备输入快照和工作环境。
5. 员工执行并与其他成员通信；平台记录文件、调用、进展和运行状态。
6. 员工提交成果版本，按项目规则进入自动检查、同行评审或人工验收。
7. 人提出意见或直接修改，平台形成新版本并计算对后续工作的影响。
8. 平台按授权调整任务，给出变更生效回执；发生异常时恢复或更换员工。
9. 达到项目验收条件后由授权人结项，整理成果、决策与有效经验。
10. 按资源策略停止运行、释放临时环境，保留可导出与可重新打开的项目记录。

## 5. 功能需求

### 5.1 项目创建与管理

- 支持自然语言创建项目；结构化维护目标、范围外事项、期限、预算及成功标准。
- 目标模糊时，提出假设和低成本验证步骤；明确区分已确认事实与待验证假设。
- 支持创建空项目和使用项目模板；首版项目模板可后置。
- 支持阶段目标和里程碑；无需套用统一行业流程。
- 项目变更保留版本和决策来源，不能覆盖历史依据。
- 状态：草稿、进行中、暂停、待结项、已完成、已取消、已归档。
- 归档是可恢复的数据组织操作；删除采用单独的数据生命周期策略。

### 5.2 员工开发工作台与员工资产库

- 创建员工模板：岗位、能力边界、工作指令、技能、工具需求、输入输出约定。
- 配置兼容的模型与运行参数，引用执行环境镜像及依赖。
- 支持隔离试运行，用样例任务和明确标准评测；显示结果、成本和失败案例。
- 模板状态：草稿、已发布、已停用。发布版本不可原地覆盖。
- 任用时固定版本，配置项目岗位、权限和知识访问范围。
- 支持暂停、替换、退出和升级；升级需通过检查并明确受影响任务。
- 在岗经验归平台保存，提炼为通用模板改进前需验证及相应授权。
- 首版以人工比较评测结果为主，不实现自动晋级或自动训练底层模型。

#### 5.2.1 员工工程管理

- 支持从空白、脚手架、已有仓库或工程包创建；已有工程导入先检查格式与依赖。
- 保留完整源文件和 Git 版本，开发草稿可以跨天继续，不因一次 AI 会话结束而删除。
- 项目运行所修改的业务代码与员工自身能力代码分开。调试可以引用样例项目快照。
- 员工开发可以邀请 AI 协作，但 AI 只在开发工作区提交修改；不得直接更新在线员工版本。
- 普通员工可以只有指令、Skills 和工具；复杂员工可以实现流程、Python 脚本或调用外部服务。不强制所有能力画成流程图。

工程建议结构（平台定义，非 Codex 内置标准）：

```text
employee-project/
  employee.yaml         身份、能力入口、资源需求、权限上限
  instructions/         岗位与能力指令
  skills/               技能及支持文件
  src/                  员工能力实现代码，可选
  tools/                工具实现与契约，可选
  workflows/            内部工作流程，可选
  schemas/              输入输出与人工表单契约
  environments/         镜像和依赖声明
  evaluations/          样例、断言、模拟资源及评测配置
  dependencies.lock     已解析的版本与哈希
```

#### 5.2.2 开发与调试体验

- 概览：能力说明、当前版本、资源需求与就绪检查结果。
- 编辑：文件树、云端 IDE、结构化配置表单；统一从版本化源定义生成运行包。
- 调试：选择能力入口、输入样例、输入文件和测试资源；预览最终上下文及其来源。
- 支持单节点试运行、完整能力试运行和从选定输入快照重新运行；重放外部操作须明确为真实执行或模拟。
- 查看节点输入输出、工具参数与结果、文件差异、耗时、成本和审批事件。
- 支持在节点边界暂停；不承诺任意模型推理位置的代码级断点。
- 对失败运行可以调整草稿后重新执行，旧记录保留，便于比较。
- 首版支持通过团队设计对话生成员工工程基础骨架、查看差异和修改草稿。复杂工具实现与跨版本自动优化后置；所有修改通过同一校验和发布流程。

#### 5.2.3 发布与维护

发布门槛：定义有效、依赖可解析、输入输出契约有效、需要的工具可实际调用、规定评测通过、权限变更明确、源版本与环境可追踪。

发布生成不可变包，包含员工版本、源码提交、依赖锁和评测摘要。包中保留资源槽位及凭据引用声明，不含实际密钥、业务私有数据和开发日志。

项目选择固定版本；升级展示能力、契约、权限和环境差异，必要时进行项目样例验证。回退员工版本不自动回滚业务数据或部署。

### 5.3 团队与协作

- 支持一项任务有一个最终责任人和多个协作者。
- 支持并行分工、顺序交接、委托、评审、专题讨论。
- 委托检查权限、资源与任务范围；员工不能自行无限扩大团队。
- 交接记录成果版本、说明和必要输入；接收者可以接受或退回。
- 首版使用列表配置团队关系，关系图作为查看能力可后置。
- 讨论有责任人、结束条件和预算；无法解决的冲突升级给指定负责人。
- 依赖图禁止形成无法执行的循环。迭代工作通过新一轮任务明确表达。

### 5.4 工作规划与任务调度

- 支持人手动创建任务、AI 提出任务和按预设规则生成任务。
- 任务可以分配给人或 AI；人类任务通过待办和成果提交推进。
- 每项任务包含目标、输入版本、负责人、优先级、依赖、交付约定和验收方式。
- Python 调度服务按依赖、权限、预算和可用容量启动工作。
- 常规状态变化由程序处理；需要判断、重新规划或处理例外时唤醒 AI 主管。
- 等待人工或外部作业时，不要求模型保持持续推理。
- 提供暂停、取消、重试、重新分配和从有效成果继续的入口。
- 重试记录新的运行，不覆盖之前失败事实。

### 5.5 协作通信中心

- 项目讨论区、任务／成果讨论区、个人待办与通知中心。
- 支持 @ 成员、回复、附件引用、关联成果版本和问题线程。
- 消息类型包括讨论、询问、委托、交接、评审、决策和阻塞报告。
- 普通讨论不自动修改任务状态；执行性指令需要解析、权限检查和回执。
- 状态至少区分已送达、已接收处理、已完成、已拒绝。
- 只有需要处理的消息触发 AI 执行，防止通知引发无限回复。
- 未响应事项按项目策略提醒或升级；通知可合并、订阅和静音。
- 消息只在有权范围内投递；大文件通过受控版本引用传递。

### 5.6 人类决策与干预

- 决策请求包含问题、证据、选项、推荐方案、成本／时间影响和阻塞范围。
- 区分业务决策和运行权限审批，批准前者不等于扩大后者。
- 人可以修改目标、调整优先级、反馈成果、接管编辑、暂停任务和替换员工。
- 变更先保存为草稿或正式提交；提交后展示影响分析。
- 影响对象包括待执行任务、正在运行任务、待验收成果及已验收成果。
- 每个影响对象有明确处置：继续、暂停、重新运行、重新验收或保留原结果。
- 显示生效回执：哪些已更新、哪些仍等待处理、失败原因是什么。
- 人工决策过期、输入版本已变化时，提示重新检查，禁止悄悄应用旧批准。
- 暂停状态需区分请求已发出、运行已停止和外部作业仍在运行。

### 5.7 云工作空间与编辑

- 提供文件树、搜索、上传、下载、预览和打开编辑器。
- 浏览器 IDE 访问服务端受控工作目录，首版具体实现需做兼容性验证。
- 文本、代码和配置支持浏览器编辑；其他类型支持预览、下载修改后上传。
- 员工使用独立任务工作目录，正式成果以版本清单提交。
- 原始输入默认保留，修改生成新版本；共享内容不能由任意员工直接覆盖。
- 人可接管工作副本，平台暂停相应写入；同时修改通过副本和冲突处理完成。
- 首版不实现字符级多人实时协同编辑。
- 文件保存不等于业务提交；页面需提示未提交修改。
- IDE 的终端同样受环境权限限制，不能绕过项目权限访问宿主机或其他项目。

建议逻辑目录：

```text
/projects/{project_id}/
  inputs/                              原始输入
  shared/                              已发布共享资料的访问视图
  employees/{employee_id}/tasks/{id}/  员工工作副本
  deliverables/{artifact_id}/          正式成果访问视图
  feedback/                            反馈附件
```

目录只是访问视图。数据库保存身份、关系和状态；对象存储保存不可变文件版本；大型数据可通过专用存储或挂载访问。

### 5.8 成果、数据关系与验收

- 成果类型支持文档、代码、数据集、模型、图片、报告及外部结果引用。
- 每个版本记录文件清单／哈希、来源任务、作者、输入版本和生成配置。
- 记录产出、派生、使用、版本及验收关系，支持影响追踪。
- 下游绑定确定的输入版本，不自动跟随“最新文件”。
- 验收规则可组合自动检查、AI 评审和人类验收。
- 评审失败退回修改，保留原版和理由；验收通过不代表永久适用于新目标。
- 成果被新变更影响后标记需要检查，不删除原验收记录。
- 任务完成需要验收证据；Codex 一轮回复结束仅代表本轮运行结束。

### 5.9 资源、运行与外部作业

- 管理执行环境、工具连接、数据源、模型认证引用及资源配额。
- Codex Runtime 运行在独立 Worker 环境，避免长期任务占用 Web 请求。
- 训练等长作业独立保存提供方 ID、状态、配置、产物和取消结果。
- 停止 Codex 会话不自动视为取消外部作业。
- 支持运行日志、心跳、超时、取消及失败分类。
- 区分模型错误、工具错误、环境故障、缺少资料、权限拒绝和业务不满足。
- 限制任务／项目预算与无有效进展的循环次数；达到边界后形成明确待办。
- 调用成本无法精确获取时标记估算或不可用，不能显示为零。

### 5.10 组织知识与改进

- 保存项目事实、规范、决策、经验及适用范围。
- 知识状态：待验证、有效、已替代、已废弃。
- 加载上下文时按任务相关性和权限选择资料，保留引用版本。
- 员工提出知识更新建议，按规则验证后生效。
- 同类错误和返工记录可用于改进模板，首版不自动扩大员工权限。
- 跨项目共享通过明确发布完成，避免项目私有资料被自动复用。

### 5.11 项目看板、导出与结项

- 首页展示目标、阶段进度、最新成果、当前活动、阻塞和待处理事项。
- 显示最近一次访问以来的关键变化，支持展开完整时间线。
- 进度基于任务和里程碑事实；探索性工作不伪造精确完成百分比。
- 提供时间、成本、验收通过率、人工介入和返工统计。
- 结项生成成果目录、验收依据、遗留问题和经验建议。
- 支持导出清单及可访问文件；未包含的外部大文件明确列出原因和引用。
- 首版提供服务端备份恢复流程；跨平台一键导入后置。

### 5.12 项目模板中心

- 主要创建入口为“与 AI 一起设计团队”，手动装配、导入和已有模板作为其他入口。对话和表单操作同一结构化草稿。
- 项目模板定义目标输入、岗位能力要求、默认员工版本、阶段、协作流程、资源槽位及验收标准。
- 支持表单装配及 YAML／源码编辑，二者映射到统一规范化定义。修改需完整校验，避免各自保存不同事实。
- 岗位引用能力要求与默认员工，创建项目时可以替换兼容员工或分配给人。
- 提供变量和数据来源选择器，能引用指定节点的指定成果，不依赖“最近一条输出”。
- 校验未绑定岗位、缺失变量、无效跳转、输入输出类型不匹配、权限与资源冲突。
- 支持使用模拟员工和测试数据预演；正式发布时固定员工、流程、技能及环境依赖。
- 从模板创建项目生成快照；更改模板不会影响已创建项目。项目内的局部调整记录差异，可另行提炼为新模板草稿。
- 导入包进入草稿并做兼容检查；展示缺失资源和重复资产处理选项，不直接执行导入代码或启用连接。
- 导出 manifest、模板定义及依赖清单；便携包可包含允许分发的固定依赖版本。禁止导出凭据值。

### 5.13 工作流程与两级组织

项目协作流程回答“谁来做、依赖谁、何时交付”；员工内部流程回答“这个员工如何实现某项能力”。二者使用可复用的节点及运行基础设施，通过子运行关系关联，分别维护作用域、预算和权限。

| 节点类型 | 行为 |
|---|---|
| AI 工作 | 调用指定员工能力或内部 Codex 工作单元 |
| 工具／脚本 | 执行已声明工具或代码入口，返回结构化结果 |
| 人类任务 | 将具体工作分配给人，等待人提交成果 |
| 人工批准 | 审阅指定提案版本并决定是否允许下一步 |
| 评审／检查 | 验证成果，返回结论、依据和返工建议 |
| 外部作业等待 | 提交或等待外部作业，持久化作业 ID |

首版提供顺序、条件分支、项目任务并行依赖、受限返工轮次与等待恢复。员工内部复杂并行／汇聚编辑后置；底层子运行必须能关联到项目任务。

员工内部不得绕过平台创建未登记的长期员工或扩大资源；需要其他正式员工协作时走委托接口。项目主管可从已有阶段生成计划，也可在授权下提出新增任务；不会因引入模板而失去处理模糊目标的能力。

### 5.14 输入绑定、人工表单与评审契约

- 输入支持标量、结构化数据、成果版本引用和外部作业引用。
- 定义阶段就检查必填字段、类型及引用；运行前展示解析结果，缺失变量不能静默变为空字符串。
- 记录输入数据版本与来源。不同分支不能错误读取其他分支的“上一步”输出。
- 人工表单支持文本、数字、单选、多选和说明；平台校验字段、合法选项与权限。AI 生成表单必须通过 schema 检查。
- 人工请求绑定任务、运行、提案／成果版本和处理人。拒绝进入退回、暂停或终止，不默认为成功并继续。
- 只批准原成果时直接记录验收；需要修改时创建应用决定的后续运行，记录决定和新成果的关系。
- 评审至少返回 pass、fail 或 blocked，附检查项、依据和原因。blocked 表示缺少证据或环境，不能归为通过。
- 格式错误作为执行／契约错误处理；业务不满足进入返工；工具故障进入重试。三者分别统计。
- 返工使用新运行与明确反馈，项目总预算不因跨阶段或新一轮而自动清零。

### 5.15 资源目录与环境就绪检查

- 共用技能、工具连接声明、环境模板和评测样例可版本化复用，不复制进每个项目配置中独立维护。
- 员工声明所需资源类型和操作，项目／开发环境绑定真实仓库、部署目标、数据源或计算作业服务。
- 显示声明、已绑定、连接可用、权限可用四种不同状态，不能把保存配置视为实际可用。
- 运行前检查 CLI、依赖、挂载目录、工具发现、认证及必要网络连接；失败直接形成可处理的资源待办。
- 试运行默认使用测试资源；使用真实外部资源时明确标识影响并按已有授权执行。
- 适配器需声明文件、工具、流式事件、取消、恢复等能力；不兼容能力入口不能发布为可用组合。

### 5.16 两种流程视图与需求文件

- 开发视图展示员工内部流程、节点调试和文件差异；项目视图展示人员、任务、成果和阻塞，可展开内部子运行。
- 画布与列表共享运行数据；选中节点同时定位输入、输出、日志与成果版本。首版提供查看与表单配置，不承诺任意拖线编排。
- 重试和返工展示历史轮次，不能只保留最新节点颜色。
- 需求、规划和决定在数据库版本化，生成 `intent.md` 等便于员工读取的视图。文件修改通过变更提交校验回写，不使用无控制的双向覆盖。
- 展示总耗时、排队、实际执行、人工等待和外部作业等待；并发时间有重叠时注明，不能直接相加。

### 5.17 对话式团队设计

产品目的：让用户先表达目标和协作意图，由 AI 完成团队与流程的初步装配，避免先逐项填写员工、工具和节点表单。团队方案属于项目模板中的团队与协作部分，不再建立一套重复的独立模板体系。

#### 5.17.1 聊天内容与澄清策略

- 入口支持“新建团队／项目模板”和“基于现有团队继续调整”。
- 用户可以描述需求、上传参考资料或指定可用员工；AI 主动检索有权使用的现有资产。
- 对话逐步形成目标与范围、岗位与职责、人和 AI 的分工、工作流程、数据交接、评审与决策点、资源需求及结束条件。
- 先提出合理方案，只追问会改变团队结构或工作方向的缺失信息，每轮集中少量问题。
- 已明确内容、AI 建议和待确认假设分别展示。工具参数、提示词措辞等细节可以后补，不阻塞整体草稿创建。
- 不要求用户知道 Phase、Step、MCP 等技术概念，界面优先使用岗位、工作、资料、交接和检查等业务表达。

#### 5.17.2 页面组成

| 区域 | 展示和操作 |
|---|---|
| 左侧聊天 | 提出需求、回答澄清、引用某员工或流程节点继续修改 |
| 右侧方案预览 | 团队岗位卡片、职责、流程与输入输出、人工介入点，随有效修订更新 |
| 待完善清单 | 缺失资源、未实现工具、员工细节和评测要求；区分阻塞运行和可稍后完善 |
| 状态与版本 | 展示理解中、草稿已更新、创建中、已创建、创建部分失败，支持比较和撤销 |

人员卡片与流程节点均可点击修改。用户也可直接编辑结构化字段；AI 后续修改必须基于最新版本，避免覆盖用户刚做的调整。

#### 5.17.3 自动创建规则

- 对话持续自动保存结构化草稿；目标、基本岗位、主要工作和交付关系明确后，自动生成或更新对应对象，无需再逐个创建。
- 生成内容包括项目模板草稿、岗位、工作节点、数据绑定、人工决策／评审节点、资源槽位及员工工程基础骨架。
- 优先引用合适的已发布员工版本。没有合适员工时创建独立员工工程草稿，包含职责、输入输出、指令、技能／工具需求、可选流程和初始评测样例。
- 若需要改进共享员工，创建派生草稿；不原地修改其他项目依赖的已发布员工。
- 每个生成对象显示来源设计修订、对象 ID 和创建结果；重复提交或断线重试不重复产生员工和流程。
- 可逆草稿创建默认自动进行。创建不等于发布、授予真实凭据或启动外部作业；正式运行仍遵守项目原有授权和就绪规则。
- 部分失败时保留已成功对象并显示剩余项，可继续补建；界面不能误报整套创建完成。

#### 5.17.4 创建后完善与持续对话

- 创建完成后停留在团队总览，显示“已具备什么”和“还需完善什么”，可直接进入某个员工的开发工作台。
- 员工详情支持编辑职责、指令、Skills、代码、工具、运行环境和评测，完成后发布并更新模板引用。
- 用户可以继续说“把评估交给人”“增加复核员工”“两项分析并行”，AI 更新对应部分并显示差异。
- 草稿中的调整直接保存并支持撤销；已发布模板或运行中项目的调整生成新草稿／变更请求，说明影响后按授权生效。
- 手动完善过的员工工程保留原内容，团队级调整只修改相关字段；代码冲突进入比较处理。
- 设计会话与实际项目执行聊天分开标识，避免“修改员工能力”被误解为“给在线员工下任务”。

#### 5.17.5 首版范围

P0 包含文字对话、可编辑团队预览、流程查看、现有员工匹配、基础工程骨架生成、自动创建、差异回执和待完善导航。复杂代码自动实现、通用拖线编排、模型自动训练不属于本功能的首版承诺。

## 7. 状态与一致性规则

### 7.1 任务状态

待开始 → 执行中 → 待验收 → 已完成。

另有等待决策、依赖阻塞、执行失败、已暂停、已取消。等待状态必须保存原因、责任人和恢复条件。验收退回可回到待开始；原成果与运行保留。

### 7.2 运行与任务分别管理

运行状态：排队、启动、运行中、等待输入、结束、失败、取消。

一次运行结束可能仍有后续工作。会话异常也不意味着已提交成果失效。恢复操作先检查有效成果和外部操作，再决定继续或创建新运行。

### 7.3 一致性约束

- 一个任务同时只有一个有效主执行租约；超时失效的 Worker 不能提交新正式结果。
- 消息和工具请求通过唯一 ID 去重，数据库提交和事件投递保持可恢复的一致关系。
- 不宣称外部操作能够天然“恰好一次”；重试前核查其实际结果。
- 成果版本不可变，使用新版本需明确记录。
- 并发修改使用版本检查，过期更新返回冲突而非覆盖。
- UI 断线后从已保存的事件继续读取，避免丢失完成或审批状态。

## 8. Codex 接入设计

采用自建执行环境，由 Python Worker 通过 Codex SDK／app-server 控制 Codex CLI 运行时。模型推理由配置的云端服务提供，当前桌面客户端不作为生产依赖。

Codex 项目主管负责需要判断的规划工作；Python 服务负责权限、调度、一致性和资源限制。平台数据库是项目事实来源。

定义 `CodexRuntimeAdapter`，隔离启动、继续、事件消费、中断和恢复等版本差异。具体能力必须在锁定版本上实测，不能直接假定桌面客户端的插件、工具或历史均能复用。

平台工具示例：`get_project_context`、`create_task`、`send_message`、`submit_artifact`、`request_review`、`request_decision`、`report_blocker`、`propose_memory`。这些是拟建业务工具，不是 Codex 原生 API。

每次调用由服务端绑定空间、项目、员工和运行身份。角色指令用于指导行为，实际权限由后端、文件系统和运行环境强制执行。

长时间无输入时释放运行资源，后续事件触发继续。会话无法恢复时，从平台快照和交接资料启动新会话；已有外部作业单独恢复关联。

官方接入依据（此前已核对，实施时再次核实锁定版本）：

- Python SDK：https://learn.chatgpt.com/docs/codex-sdk
- app-server：https://learn.chatgpt.com/docs/app-server

官方文档对部分 app-server／WebSocket 能力标有实验性限制；首版优先封装服务端本地通信，前端仅连接平台 API。

## 9. 数据与技术架构

- 前端：React + TypeScript + Vite + Ant Design。
- Web 服务：Python + FastAPI，模块化单体。
- 执行层：独立 Python Worker、Codex 适配层和受控执行环境。
- 数据库：PostgreSQL，存储业务对象、状态、版本元数据、事件和审计。
- 文件层：持久工作卷与 S3 兼容对象存储，分别承载可编辑副本和成果版本。
- 事件展示：前端以 SSE 接收更新；双向终端通信通过受控连接实现。
- 异步任务：采用持久任务机制，具体队列产品在技术验证后确定。
- 浏览器 IDE：独立服务、统一身份入口、项目范围访问；具体实现待兼容性验证。

初期模块：identity、projects、employees、tasks、communications、decisions、artifacts、workspace、runtime、knowledge、audit。

本版增加 employee_development、asset_registry、project_templates、workflows、resource_bindings 和 evaluations 的逻辑边界；可以合并部署，不要求每个模块单独微服务。开发沙箱和正式 Worker 分配不同运行配置，共享版本化契约。

认证信息通过密钥引用使用，不能放入员工模板、提示词、普通日志或导出包。模型服务账号和计费按部署环境配置，不能假定个人桌面登录可直接作为多用户生产服务认证方案。

## 10. 授权与数据生命周期

默认策略建议：员工可读取授权输入、修改自己的任务工作区、提交成果；不能直接覆盖已发布成果或自行扩大权限。

授权可按项目、员工、工具、环境和操作类型配置。重大范围变更、超预算及没有事先授权的外部操作进入决策或审批；日常已授权工作直接推进。

保留工作相关操作、消息、工具结果、文件变化、审批和验收记录。大输出允许截断展示但保留可访问原件或明确存储策略；敏感值先脱敏。

归档不删除数据。删除、保留期限、备份周期、恢复目标与空间配额需在正式部署前确定。退出项目的员工或人失去访问权限，其已归属项目的成果继续保留。

## 11. 首版范围建议

### P0：首版必须形成闭环

- 单空间、多项目、基本人类成员与权限。
- 对话式团队设计：结构化草稿、实时预览、自动创建、现有员工引用与基础工程骨架、细节完善导航。
- 创建项目，明确目标、输入及验收标准。
- 员工源工程、浏览器编辑、能力入口、依赖声明、基础调试评测、不可变发布和任用。
- 项目模板基础装配、输入绑定、发布快照及资产包导入导出。
- 基础流程节点、结构化人工表单、评审契约与受限返工。
- 资源目录与就绪检查，工具声明到实际执行贯通。
- 一个 AI 主管与可配置专业员工，支持人类任务。
- 任务依赖、运行管理、交接、消息和决策待办。
- 文件上传预览、云端文本编辑、成果版本与人工验收。
- 人工变更、逐项影响处置和生效回执。
- 暂停、重试、员工替换和中断恢复。
- 项目知识、可追踪活动、基础成本与预算限制。
- 项目结项、导出清单、备份恢复流程。

首版影响分析可由 AI 提议、人在必要时确认，不要求自动理解任意文件内容的全部依赖。

### P1：闭环稳定后扩展

- 更丰富的项目模板库、团队关系图和复杂流程可视化编辑。
- 在对话式基础创建之上扩展复杂员工代码与工具自动开发、跨版本批量评测和员工内部复杂并行编排。
- 大型数据集、模型产物的专用预览与对比。
- 标准化外部训练作业适配器。
- 更完整的自动评测、通知策略、经验提炼和跨项目共享。
- 高级权限、成本分析及跨项目资源调度。

### 暂不纳入

独立员工市场、完整模型训练基础设施、自动员工晋级、通用字符级协同编辑、跨平台一键迁移、完全无人监督的任意外部业务执行。

## 12. 验收场景

| 编号 | 场景 | 通过条件 |
|---|---|---|
| A01 | 模糊目标创建 | 形成可编辑方案，明确假设、缺少资料和首个成果 |
| A02 | 员工任用 | 固定模板版本，实际工具和目录权限与配置一致 |
| A03 | 员工协作 | 上游提交具体版本，下游接受或退回，责任归属可查 |
| A04 | 人类参与 | 人类收到任务并提交成果，后续 AI 工作正确启动 |
| A05 | 修改反馈 | 人提交新版本，平台列出影响并显示实际生效情况 |
| A06 | 并发编辑 | 人接管时不会被 AI 覆盖，冲突可发现和处理 |
| A07 | 员工替换 | 替换后可使用已保存状态继续，原员工不能继续提交 |
| A08 | 故障恢复 | Worker 中断后任务可恢复，不重复产生已确认的外部操作 |
| A09 | 预算与循环 | 到达配置阈值停止新增执行，展示原因和处理入口 |
| A10 | 验收结束 | 有验收证据才完成，结项后按规则释放资源 |
| A11 | 数据归属 | 退出成员失去权限，项目仍保留完整成果与来源 |
| A12 | 通知断线 | 浏览器重新连接后能获得遗漏状态，消息不会重复执行 |
| A13 | 长作业适配验证 | 使用测试作业验证会话中断不丢失作业、取消结果独立显示 |
| A14 | 备份恢复 | 在测试环境恢复项目元数据和对应成果版本，关联一致 |
| A15 | 独立开发 | 没有正式业务项目时也能创建、编辑、调试员工工程，开发中断不丢源码 |
| A16 | 版本隔离 | 修改员工或项目模板草稿不影响运行实例，发布后升级须明确选择 |
| A17 | 输入契约 | 缺失必填参数或绑定错误在执行前显示；多上游数据来源可追踪 |
| A18 | 工具贯通 | 从资源声明到绑定、发现、实际调用均有证据，只有配置不能通过 |
| A19 | 人工拒绝 | 拒绝指定提案后不以成功推进，过期批准不能作用于新版本 |
| A20 | 评审返工 | 格式错误、业务失败和缺少证据分开处理，返工轮次及预算有限 |
| A21 | 资产可移植 | 导出再导入后定义一致，缺失资源需绑定，包内不含凭据值 |
| A22 | 子运行追踪 | 项目任务可展开员工内部步骤，能反查输入、成果、决定及历史运行 |
| A23 | 重规划生效 | 当前步骤结束后新计划能接续，旧运行与旧工单被正确替代 |
| A24 | 真正取消 | 取消传播到执行者，停止回执可信，旧运行迟到结果不能覆盖新状态 |
| A25 | 对话设计团队 | 用户用自然语言描述目标，可形成岗位、工作流、交接与决策点的结构化可编辑草稿 |
| A26 | 自动创建 | 对话信息足够后生成对象并给出映射；已有员工被引用，缺失员工生成独立工程草稿 |
| A27 | 创建幂等与恢复 | 重发、刷新和部分失败恢复不会产生重复员工或节点，创建结果准确显示 |
| A28 | 渐进完善 | 未提供工具凭据仍可创建草稿，待完善清单准确；补齐后可试运行和发布 |
| A29 | 混合编辑一致 | 用户手动改过员工细节后继续聊天，无关修改被保留，冲突明确处理 |
| A30 | 草稿与运行边界 | 对话创建不会自动改写已发布资产或启动真实外部作业，运行中修改进入变更流程 |

首版主验收案例建议采用数据分析项目：准备输入 → 分析 → 评审 → 人修改 → 重做受影响部分 → 替换员工 → 恢复 → 验收。训练作业使用适配器测试场景验证生命周期，避免首版依赖完整 GPU 平台。

## 13. 质量和非功能要求

- 隔离：权限检查覆盖 API、消息、文件、IDE 和工具执行。
- 可恢复：重启服务后，持久任务、成果和待办仍可追踪。
- 可解释：用户能看到决策依据、数据来源和可观察操作结果。
- 可用性：模型等待、工具等待、缺少输入及系统失败具有不同展示。
- 可测试：调度与权限可通过模拟员工测试；另有真实 Codex 集成验证。
- 性能：业务接口与模型运行分离，长任务不阻塞工作台。
- 容量：上线前明确并发员工数、文件大小、运行时长和空间配额，并执行对应负载测试。
- 性能时延、可用性及备份恢复的数值目标，在部署规模确认后制定，本文不把未测试指标作为承诺。

## 14. 产品效果指标

以相似任务的人工基线比较，分别记录质量、时间和成本，不只统计模型输出量。

- 成果首次验收通过率与最终通过率。
- 人工投入时间：解释、确认、检查、修订和故障处理。
- 项目／任务交付周期及等待时间。
- 变更反馈到实际生效的时间。
- 员工替换和故障恢复成功率。
- 同类错误复发率、重复工作量。
- 实际模型与计算成本；缺失数据单独标记。

首个试点先建立基线，再确定扩展门槛，不以预设“自动化率”代替业务价值。

## 15. 实施顺序与阶段出口

1. 接入验证：Python 控制 Codex，验证事件、文件、工具、中断和认证方式。出口：可重复运行的集成验证。
2. 员工开发闭环：创建工程、编辑、资源绑定、试运行、评测、发布。出口：未创建正式业务项目也能开发员工。
3. 对话创建与项目闭环：聊天设计团队、自动生成模板与员工草稿、完善并发布、版本任用、主管规划、输入绑定、执行、消息、交接与验收。出口：完成非软件研发场景。
4. 人工干预：编辑、反馈、影响分析和生效回执。出口：变更正确影响后续任务。
5. 可靠性：暂停、恢复、替换、预算、权限及备份。出口：A01—A30 首版场景通过；A13 可用测试作业适配器验证。

以上为顺序建议，开发工期在接口验证与页面范围确定后估算。

## 16. 主要风险与处理方向

| 风险 | 处理方向 |
|---|---|
| 模型把猜测当事实 | 显式假设、来源引用、验收与知识验证 |
| 员工无限讨论或反复重做 | 预算、讨论结束条件、主管升级与人工决策 |
| 多人／多员工覆盖文件 | 工作副本、不可变版本、写入租约和冲突检查 |
| 一条自然语言消息被误当授权 | 结构化动作、权限检查、清晰回执 |
| CLI 升级破坏集成 | 固定版本、适配层、升级验证与回退 |
| 项目依赖长期单一会话 | 平台持久状态、交接资料和新会话重建 |
| IDE 与工具绕过权限 | 环境隔离和统一凭据边界 |
| 长任务停止不彻底 | 外部作业单独跟踪，停止状态明确区分 |

## 17. 本轮需要确认的产品选择

以下为建议默认值，尚未视为用户已批准：

| 选择 | 建议默认值 | 影响 |
|---|---|---|
| 首版用户范围 | 自己团队使用，单组织空间、多用户、多项目 | 决定认证及组织复杂度 |
| 项目主管 | 每个项目默认配置一名，可暂停自动规划 | 决定日常协调入口 |
| 首版试点 | 数据分析与报告项目 | 验证通用性，降低外部基础设施依赖 |
| 员工建立方式 | 独立源工程开发、基础流程／代码、调试评测后发布任用 | 员工开发成为首版核心功能，仍不训练 Codex 底层模型 |
| 人类成员 | 可以承担任务和交付成果 | 支持真正的人机混合团队 |
| 编辑协作 | 预览／评论／直接编辑，首版不做字符级协同 | 决定编辑器集成范围 |
| 变更执行 | 已授权、可明确判断的变更直接生效；重大或有歧义变更请求决策 | 平衡自主性和控制 |
| 首版资源 | 单机可启动，Worker 和文件层可后续扩展 | 需结合现有服务器确定 |
| 员工工厂边界 | 平台内独立工作台、独立工程和运行环境，暂不独立产品 | 保留接口和发布契约，后续可拆分 |
| 项目模板 | 首版支持基础装配、版本锁定、预演与导入导出 | 将原 P1 的模板基础提升至 P0 |
| 对话式团队设计 | 用户已明确要求作为主要入口；P0 包含团队／流程草稿与基础员工工程自动创建 | 复杂员工代码和工具自动开发仍在 P1；具体交互规则为本版建议 |
| Orbit 采用方式 | 吸收设计，按 Python 后端重新实现必要能力 | 不直接把 Orbit 当作已可用生产引擎 |

尚需在部署前明确：服务器环境、Codex 生产认证与计费、并发规模、存储配额、数据保留期限、备份恢复目标及外部系统接入范围。
